# Windows build, package and launch (not run in cloud)

## Prerequisites

- Windows x64. Initial SDK target: Windows 10 build 19041; qualify actual supported
  Windows 11 and Windows 10 installations separately. The SDK floor is not a
  guarantee that a given OS/support lifecycle or Bluetooth driver is suitable
- Existing Visual Studio 2022 with Desktop development with C++, .NET desktop
  development, MSIX/Windows Application Packaging Project tooling and Windows SDK
- .NET 8 SDK. Use official Microsoft installers if missing; installing software
  or approving package trust is an operator task, not performed by this prototype
- A BLE adapter/driver with `BluetoothAdapter.IsPeripheralRoleSupported == true`

## Compile native code and application

From the x64 Native Tools Command Prompt for Visual Studio, in the project root:

```bat
scripts\build-native.cmd
dotnet build Windows\DigitWindowsBLE.csproj -c Release
```

The first command builds `build\digit_queue.dll` and runs the real queue tests.
The DLL uses the static MSVC runtime. It is copied alongside the x64 .NET app.
The WinRT adapter build is a mandatory first Windows gate; this command has not
been executed in the cloud. Do not treat source inspection as a compiler pass.

## Give the app package identity

Use Visual Studio's Windows Application Packaging Project workflow:

1. Create a solution containing the existing `Windows\DigitWindowsBLE.csproj`
2. Add a Windows Application Packaging Project named `DigitWindowsBLE.Package`,
   target/minimum version 10.0.19041.0 or a newer supported SDK you are qualifying,
   and select x64 for both projects
3. Add the existing DigitWindowsBLE application as the package application
   reference and entry point. Retain the generated full-trust desktop application
   declaration and `runFullTrust` restricted capability where the template uses it
4. Edit the package's Package.appxmanifest XML to add the following inside its
   existing `Capabilities` element (this is distinct from Windows/app.manifest):

```xml
<DeviceCapability Name="bluetooth" />
```

5. Supply development identity and icons through the packaging designer. Do not
   impersonate a shipping device or company. Use Visual Studio's normal local
   development package deploy/debug workflow and approve any certificate/trust
   steps yourself. No signing credential is included in this source bundle
6. Set the packaging project as startup, deploy, then launch the packaged app

The included project is the controller application; the packaging project is
intentionally generated by the actual installed Visual Studio template. It is
not a prebuilt or signed installation package. Launching the EXE without package
identity fails closed at Publish. The app has no network capability or network
listener in its own source; the generated package must not add unnecessary
capabilities. Confirm actual capabilities on the deployed package.

## Windows verification record

Record the OS build, CPU architecture, .NET/SDK/MSVC versions, compile output,
package identity/capabilities, adapter hardware ID and driver version. Launching
successfully only passes the app stage. Starting advertising only passes the
GATT stage. Pairing and real HID input each require their own evidence.

Do not attempt Windows classic-HID L2CAP/PSM injection, private driver interfaces,
registry hacks or reserved-service workarounds if a qualification gate fails.
